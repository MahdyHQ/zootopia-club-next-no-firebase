2. CURRENT TRUTH SNAPSHOT
================================================================================

As of 2026-04-13, the project is a Next.js 16.2.2 monorepo deployed on Vercel,
using Supabase as the unified backend provider (Postgres database, Auth, Storage).

Key verified facts:
- Firebase has been fully replaced by Supabase (no Firebase runtime dependencies)
- Auth.js (NextAuth v5) with JWT strategy manages sessions
- Supabase Auth provides identity (email/password only)
- Two credential providers: user-credentials and admin-credentials
- Admin access controlled by email allowlist (ZOOTOPIA_ADMIN_EMAILS)
- Profile completion gating blocks incomplete profiles from protected features
- AI providers: Google AI (Gemini) and DashScope (Qwen/Alibaba)
- Tool default models are now server-authoritative per real tool via
  `ZOOTOPIA_DEFAULT_MODEL_ASSESSMENT` and `ZOOTOPIA_DEFAULT_MODEL_INFOGRAPHIC`,
  with strict tool-scoped fallback validation
- Assessment export/result artifact metadata now mirrors into
  `assessmentArtifactMetadata` documents for owner/kind/status/expiry queries
- Upload records now persist normalized `fileExtension` and `contentSha256`
  metadata for durable reporting and retention tooling
- Document uploads stored with configurable retention (default 15 min)
- Assessment results stored with configurable retention (default 1440 min / 1 day)
- Export artifacts stored with configurable retention (default 15 min)
- Assessment credits limit AI generation with env-configurable UTC renewal windows
  (default 24h, daily behavior preserved)
- Admin credit mutations now persist durable per-user before/after history
  snapshots and are rendered on `/admin/users/[uid]`
- Protected header and settings surfaces now share a compact local avatar policy
  (`admin` role override → managed `gender` asset → initial fallback)
- Email verification via Supabase with Resend provider support
- Admin panel includes user management, storage management, governance dashboard
- Database uses Supabase Postgres with RLS policies
- Migration management via scripts/supabase/apply-migrations.mjs
- 10 migration files tracked in supabase/migrations (latest adds artifact-metadata indexing + document file-extension backfill)

3. PROJECT PURPOSE & PLATFORM DIRECTION
================================================================================

Zootopia Club is an AI-powered platform that provides:

1. Document Upload & Processing
   - Users upload documents (PDF, images, text files)
   - Server-side extraction and processing pipeline
   - Configurable retention policies per storage type

2. AI Assessment Generation
   - Users generate assessments from uploaded documents
   - AI models analyze content and produce structured assessments
   - Credit-limited system (daily caps)
   - Export to PDF, JSON, and other formats

3. Infographic Generation
   - AI-powered infographic creation from document content
   - Admin-only feature (currently gated)
   - Multiple modes and styles

4. Admin Governance
   - User management and oversight
   - Storage management and cleanup
   - System governance controls
   - Audit logging

Platform Direction:
- Migrated from Firebase to Supabase (complete)
- Monorepo structure prepared for future API extraction
- Provider-agnostic AI layer (Google + Alibaba/DashScope)
- Enterprise-grade security with RLS, admin allowlists, rate limiting

4. ARCHITECTURE STYLE
================================================================================

Pattern:        Next.js App Router with layered server architecture
Style:          Monorepo with workspace isolation
Session:        Stateless JWT (Auth.js / NextAuth v5)
Database:       Supabase Postgres (provider-managed)
Storage:        Supabase Storage buckets (provider-managed)
AI:             Multi-provider orchestration (Google AI + DashScope)

Layered Architecture:
```
Route Handlers (apps/web/app/api/)
  → Session/Auth Layer (lib/server/session.ts)
  → Repository Layer (lib/server/repository.ts)
  → AI Execution Layer (lib/server/ai/execution.ts)
  → Storage Layer (lib/server/supabase-blob-storage.ts)
  → Database Layer (lib/server/zootopia-postgres-adapter.ts)
```

Boundaries:
- Frontend: Client components in (site), (public), (protected)/(completed)
- Backend: Route handlers, lib/server/*, auth.ts, proxy.ts
- Shared: packages/shared-* (types, config, utils)
- Infrastructure: supabase/migrations/, scripts/, vercel.json
- Provider-Managed: Supabase (Auth, Postgres, Storage), Vercel (Hosting), Resend (Email)

Same-Origin vs Provider-Managed:
- Next.js app runs on Vercel (same-origin for all /api/* routes)
- Supabase Auth: cross-origin provider (browser → Supabase CDN)
- Supabase Postgres: server-side only (connection string, not browser-accessible)
- Supabase Storage: cross-origin provider (browser + server)
- Google AI API: cross-origin provider (server-side calls)
- DashScope API: cross-origin provider (server-side calls)
- Resend/SMTP: server-side only

12. AUTH & SESSION ARCHITECTURE
================================================================================

Framework: Auth.js (NextAuth v5)
Strategy: JWT (stateless sessions)
Identity Provider: Supabase Auth (email/password only)

Credential Providers:
1. user-credentials — Regular user login
2. admin-credentials — Admin login (separate provider)

User Login Flow:
1. Client signs in via Supabase browser client → receives idToken
2. Client calls signIn("user-credentials", { idToken, ...deviceMetadata })
3. Server (auth.ts → authorizeUserCredentials):
   a. Runtime check: Supabase admin runtime + allowlist must be configured
   b. Rate limit: 20 requests/minute per IP
   c. Token verification: verifySupabaseAccessToken() via Supabase getUser()
   d. Recency check: auth_time must be within 5 minutes
   e. Admin block: If email in ZOOTOPIA_ADMIN_EMAILS, reject with ADMIN_LOGIN_REQUIRED
   f. Provider check: Must be password provider
   g. User upsert: upsertUserFromAuth() creates/updates profile in Postgres
   h. Status check: User must be active (not suspended)
4. JWT callback populates token with uid, role, status, profile completion
5. Session callback syncs token to session object
6. Client receives session cookie

Admin Login Flow:
1. Admin signs in via Supabase browser client
2. Client calls signIn("admin-credentials", { idToken })
3. Server checks email against ZOOTOPIA_ADMIN_EMAILS allowlist
4. If not in allowlist, reject
5. If in allowlist, proceed with same verification as user flow
6. JWT populated with role: "admin"

Session Configuration:
- Strategy: JWT (no database sessions)
- Max age: ZOOTOPIA_SESSION_TTL_SECONDS (default 3600 = 1 hour)
- Cookie: httpOnly, secure, sameSite: lax

Key Files:
- apps/web/auth.ts — Auth.js configuration
- apps/web/proxy.ts — Auth.js proxy helpers
- apps/web/lib/auth-*.ts — Auth utilities
- apps/web/lib/server/session.ts — Server session utilities

14. PROFILE COMPLETION & USER GATING MODEL
================================================================================

Profile Completion Gating:
- Users must complete their profile before accessing protected features
- Incomplete profiles are redirected to /settings to finish setup
- Profile completion status stored in JWT session token
- Gating applied at:
  - Route level (middleware or layout guards)
  - API level (server-side checks in route handlers)

Gating Rules:
1. User logs in → session created
2. Session checked for profile completion
3. If incomplete → redirect to /settings
4. If complete → access to protected routes
5. Admin users bypass profile completion gating

Profile Fields (typical):
- Display name
- Phone number (validated with libphonenumber-js)
- Preferences (theme, locale)
- Any required onboarding fields

Implementation:
- Profile completion check in session token
- Server-side guards in API routes
- Client-side guards in protected layouts
- Redirect logic in auth flow

15. UPLOAD / DOCUMENT / STORAGE FLOW
================================================================================

Upload Flow:
1. User selects file on /upload page
2. Client validates file type and size
3. File sent to POST /api/uploads
4. Server validates file, extracts metadata
5. File stored in Supabase Storage bucket
6. Metadata saved to Postgres via repository
7. Upload record created with owner_uid
8. Response includes upload ID and metadata

Document Processing:
- document-runtime.ts handles processing pipeline
- Metadata extraction (file type, size, name)
- Storage path generation
- Retention policy application

Storage Retention:
- Uploads/documents: 15 minutes (configurable via ZOOTOPIA_UPLOAD_RETENTION_MINUTES)
- Mode: expiry (automatic deletion after retention period)
- Configurable per scope via env vars

Storage Operations:
- supabase-blob-storage.ts handles all storage operations
- Upload, download, delete, URL generation
- Bucket management and cleanup
- Admin storage cleanup endpoint: POST /api/admin/storage/cleanup

File Types Supported:
- PDF documents
- Images (PNG, JPG, etc.)
- Text files
